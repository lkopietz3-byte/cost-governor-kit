# A visual studio for your tools

September 30, 2026. Original experiences and creative identity lead; portfolio, PlanrLabs, app usefulness and marketing are the practical second payoff. Ranking here is engineering and product judgment, not measured revenue or time savings.

The strongest foundation is **one real mechanism, an inspectable result, and several useful presentations of that result**. Threshold implements this for Cost Governor. It gives the technical work a memorable visual identity while teaching something a normal SDK README makes hard to see.

The working instrument now closes a more useful loop: **ask a question → run it → understand the result → change one boundary → compare actual outcomes → keep the conditions**. Its new explanation comes from the recorded SDK facts; suggestions prepare a draft rather than predict a result. The baseline comparison pairs completed work with known estimated spend. A local notebook preserves named conditions; exported journals preserve evidence. This pattern is ready to inform the next native adapter, while a shared multi-tool package should wait for a second actual consumer.

## Make progress visible at the right level

Use three explicitly named modes:

- **Recorded:** a captured result or journal, like Threshold replay and Foundation comparison.
- **Observed:** callbacks/events actually emitted by the currently running owner. Use counts and known states; show an unknown or disconnected state when observation stops.
- **Proposed:** a storyboard, decision, planned next action, or unrun improvement. Keep its approval/result empty until that event actually occurs.

Do not infer execution from a file existing or task completion from an animation ending. An elapsed timer is useful only if it measures a real operation. For a known batch, show finished attempts and planned total. For an open-ended process, show the actual phase, latest event and observation age.

Give each mechanism its own visual grammar: a circuit for admission, pinned rails for evidence comparison, a light table for artwork versions, a timeline for native rendering, and anchored links for an audit chain. Reuse accessible controls, spacing, state labels, export behavior and source identity. This is a shared implementation foundation with distinct experiences.

## The assembly line

1. **Choose the owner and real task.** Reopen the source and current result. Write one sentence saying what a person should understand or accomplish.
2. **Instrument one boundary.** Observe existing callbacks or consume an existing structured result. Keep the useful domain fields: amounts, units, operation IDs, statuses, timestamps and source hashes. No general scheduler is needed for this step.
3. **Build the instrument.** The main view should explain what entered, the decisive condition, what ran, what changed, and what remains unresolved. A selection should lead to the exact record behind a shape.
4. **Exercise the consequential branches.** A pleasing successful path is insufficient if a refusal, failed confirmation, unavailable file or stale result becomes visually misleading.
5. **Freeze the journal.** Keep the source revision, input identity and bounded result with it. Replay changes presentation, not the result.
6. **Produce the demonstrations.** Capture the actual page, keep the source/synthetic labels visible, and export a short result summary. Use the same source journal for a still, clip, walkthrough and case study.
7. **Reuse in the next owner.** Extract the shared event/view helpers only after a second real adapter exposes a compatible need. Each owner retains its execution and domain contract.

Threshold already covers steps 1–6 for a local Cost Governor example. External publication, app adoption, production adapters and measured demand remain separate work.

## Where the installed programs add real value

**Obsidian: a visible creative index.** Keep one note per instrument or original work, with `owner`, `source`, `status`, `proof`, `preview`, `next_action`, and `decision`. Use a Base for sortable status/owner views and a Canvas to show how a source becomes an experience. Current documentation supports multiple configured views and community-provided custom layouts; the developer API supports custom views over note properties. The inspected local app is 1.13.7, while current help lists native Kanban at 1.14, so use its available table/cards/Canvas now. A custom Bases view is a promising later native UI experiment in a separate development vault, once the ordinary note/index path earns its place. [Views](https://obsidian.md/help/bases/views), [custom Bases views](https://docs.obsidian.md/plugins/guides/bases-view).

**Canvas as a portable map.** JSON Canvas describes text, file, link and group nodes plus connecting edges. That lets the studio map source ownership and handoffs without installing a synchronization engine. The supplied Visual Assembly canvas is such a map, not an execution graph. [JSON Canvas specification](https://jsoncanvas.org/spec/1.0/).

**Blender: authored object and motion identity.** Use the already exercised Form & Flow source-to-GLB/poster route for meaningful spatial assets, cinematic framing or a family of original objects. Geometry Nodes is a useful next extension when repeated accepted geometry needs shared controls. Keep a separate browser preview check: native lighting/material/rig behavior does not automatically transfer to glTF. The local scenes already prove one export path; that does not establish cloth/character portability. The current exporter documentation describes geometry-node instance export and optional GPU instancing. [Blender glTF exporter](https://docs.blender.org/manual/en/latest/addons/scene_gltf2.html).

**Arsenal: composition and delivery.** Use it for the real source plates, versions, native timeline, render settings and checked film. Feed it the output of an accepted instrument/scene. Improve its existing catalog/reader UI rather than creating a second source database. The earlier Form & Flow importer experiment did not prove a new Arsenal composition render.

**Browser + code: the live explainer.** SVG/CSS are strong for readable gates and state paths; WebGL/glTF are useful when object/spatial interaction matters. Threshold needed lightweight geometry and direct SDK calls. Form & Flow needed actual 3D. Pick the medium that explains the task, and keep a static reading/reduced-motion path.

**Editing tools: finish one captured result.** The generated WebM clips are silent captures of the real Threshold page. A later native editor can add music, narration and reframing if its import/export path is verified. Avoid starting a new design/editor migration before that concrete output is useful. Playwright provides local browser recording; recordings finalize when the context closes. [Recording documentation](https://playwright.dev/docs/videos).

**AI: semantic judgment where it changes a decision.** Codex handles implementation and deterministic verification here. A bounded Jev judgment can later rank creative alternatives or turn an ambiguous request into a typed routing decision, with its actual input/output, tokens, estimated cost and no-Jev baseline visible. A separate reviewer can challenge a consequential assumption. Arithmetic, source hashing and exact execution statuses should remain deterministic. No provider/Jev call was needed for Threshold.

## Prompts that produce a distinctive result

Use these with the actual owner source and an existing working result; the prompt alone supplies no execution evidence.

### Design a visual instrument

> Read the current implementation and its output contract. Choose one useful mechanism and one visual metaphor that makes its decisive condition obvious. Show the input, the decision, the work that actually ran, the state that changed, and the unresolved outcome. A click on a shape must reveal the underlying record. Use expressive typography, precise units, sparse color roles and meaningful motion. Deliver one real callback/result adapter, keyboard and phone behavior, a static/reduced-motion path, and a recorded showcase drawn from the same journal. Explain uncertainty at the point where it changes interpretation.

### Upgrade Foundation's comparison reader

> Start from the current studio_status comparison result and existing HTML reader. Build an Evidence Loom: two pinned snapshot rails, explicit field-change threads, a clear integrity break, and the actual pending-review state. Reuse the recorded_state, changed_fields, counts, source hashes and unavailable branches. Playback represents the supplied snapshots; live observation remains unobserved. Prove one changed-state case and one damaged-evidence case, preserving the current CLI and other dirty work.

### Make an honest, impressive product showcase

> Capture a finished working interaction at a readable composition. Let an actual condition change cause a visible path and result change. Keep the source, local/synthetic scope and unresolved branch readable. Begin with the mechanism, reveal the consequence, and end on the useful output. Produce a short silent master, a still, the exact run/recipe and a case-study paragraph stating what was implemented, exercised and not established. Add music/narration only through a verified native edit/export path.

### Grow original IP with the foundation

> Use one authored premise, one memorable object or character silhouette, and one emotionally meaningful interaction. Give the setting a coherent material, color and sound identity. Build one complete scene with a beginning, a choice and two distinct consequences. Preserve the editable native source and a browser reading path. Make the scene valuable as an original work first; derive the trailer and portfolio explanation from the actual experience after it works.
